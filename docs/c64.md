# Zielplattform: Commodore 64

> **Stand 0.3:** Speicherkarte, Bausteinregister mit Schreibprotokoll, Rasterzähler, CIA-1-Timer A und die
> KERNAL-Emulation sind umgesetzt (`m6510::C64`, `m6510::Kernal`). Geplant: der Bildschirm als Bild (0.5) und
> Disk-/Tape-/Cartridge-Images (0.6). Registernamen und KERNAL-Adressen stammen aus *Mapping the Commodore 64* bzw. dem
> *Programmer's Reference Guide* und sollten bei Gelegenheit noch einmal gegen die Quellen geprüft werden.

Entsprechung in den Schwesterprojekten: Amstrad CPC (Z80) und Amiga 500 (MC68000). Wie dort gilt: der Prozessorkern bleibt
maschinenunabhängig, die Maschine hängt über Bus-Schnittstelle und Hooks an ([architecture.md](architecture.md)).

## Speicherlayout

| Bereich | Inhalt (Standardkonfiguration `$01 = $37`) |
|---|---|
| `$0000–$0001` | Prozessorport (Richtung, Daten) |
| `$0002–$00FF` | Zero Page; von BASIC und KERNAL stark belegt, frei z. B. `$FB–$FE` |
| `$0100–$01FF` | Stapel |
| `$0200–$03FF` | Arbeitsbereich von BASIC/KERNAL; RAM-Vektoren `$0314` (IRQ), `$0316` (BRK), `$0318` (NMI), `$031A–$0332` (KERNAL-I/O) |
| `$0400–$07FF` | Bildschirmspeicher (Standard), `$07F8–$07FF` Sprite-Zeiger |
| `$0800–$9FFF` | BASIC-Programmspeicher (erste Zeile bei `$0801`) |
| `$A000–$BFFF` | BASIC-ROM (8 KiB) oder RAM |
| `$C000–$CFFF` | RAM |
| `$D000–$DFFF` | I/O, Zeichensatz-ROM oder RAM |
| `$E000–$FFFF` | KERNAL-ROM (8 KiB) oder RAM |

I/O-Bereich (wenn eingeblendet):

| Bereich | Baustein | Bemerkung |
|---|---|---|
| `$D000–$D3FF` | VIC-II | 47 Register, alle 64 Byte gespiegelt |
| `$D400–$D7FF` | SID | 29 Register, alle 32 Byte gespiegelt; `$D419–$D41C` lesbar |
| `$D800–$DBFF` | Farb-RAM | 1000 Halbbytes (4 Bit; obere Bits lesen sich unbestimmt) |
| `$DC00–$DCFF` | CIA 1 | Tastatur, Joysticks, Timer → IRQ |
| `$DD00–$DDFF` | CIA 2 | VIC-Bank (Bits 0–1 von `$DD00`, invertiert), serieller Bus, Timer → NMI |
| `$DE00–$DFFF` | I/O 1 / I/O 2 | Cartridge-Erweiterungen |

## Speicherkonfiguration (`$01`)

Ohne Cartridge bestimmen die Bits 0–2 von `$01` (`LORAM`, `HIRAM`, `CHAREN`), was der Prozessor sieht:

| `$01` & 7 | `$A000–$BFFF` | `$D000–$DFFF` | `$E000–$FFFF` |
|---|---|---|---|
| `0`, `4` | RAM | RAM | RAM |
| `1` | RAM | Zeichensatz-ROM | RAM |
| `2` | RAM | Zeichensatz-ROM | KERNAL |
| `3` | BASIC | Zeichensatz-ROM | KERNAL |
| `5` | RAM | I/O | RAM |
| `6` | RAM | I/O | KERNAL |
| `7` | BASIC | I/O | KERNAL |

- **Schreiben** geht immer ins RAM – auch unter eingeblendetem ROM. Nur bei eingeblendetem I/O treffen Schreibzugriffe die
  Bausteine.
- Cartridges ändern die Karte über die Leitungen `EXROM`/`GAME` (8K: ROML `$8000–$9FFF`; 16K: zusätzlich ROMH `$A000–$BFFF`;
  Ultimax: ROMH bei `$E000`, viel Speicher unbelegt). Umsetzung mit CRT-Unterstützung (Meilenstein 0.6).
- Die **VIC-II-Sicht** ist eine andere: Der VIC sieht immer RAM aus einer 16-KiB-Bank (`$DD00`), in den Bänken 0 und 2
  zusätzlich das Zeichensatz-ROM bei `$1000–$1FFF` bzw. `$9000–$9FFF`, und das Farb-RAM direkt. Der Video-Renderer
  benutzt diese Sicht.

## Geräte: Register mit Schreibprotokoll

Wie beim Amiga-500-Profil des MC68000-Projekts gibt es **keine Gerätemodelle**, sondern Register als Speicher:

- Jeder Schreibzugriff auf VIC-II, SID, CIA 1/2, Farb-RAM und I/O 1/2 kommt ins **Schreibprotokoll** (`io`): Adresse
  (Spiegeladressen auf das Grundregister abgebildet), Wert, PC des schreibenden Befehls, Baustein, Registername nach
  *Mapping the Commodore 64* (`EXTCOL` für `$D020`, `SIGVOL` für `$D418`, `CIAICR` für `$DC0D` …). Read-Modify-Write-Befehle
  erscheinen zweimal (alter, dann neuer Wert) – wie auf der Hardware, `INC $D019` quittiert so einen VIC-Interrupt.
- Lesen liefert den zuletzt geschriebenen Wert, mit diesen Ausnahmen:
  - **Rasterzeile** `$D012` (Bit 8 in `$D011`) = (Zyklenzähler / 63) mod 312 (PAL). Warteschleifen auf eine Rasterzeile
    enden also nach der passenden Zeit, ohne Seiteneffekt beim Lesen.
  - **Raster-Interrupt:** Erreicht die Rasterzeile den Vergleichswert, wird Bit 0 von `$D019` gesetzt; mit `$D01A` Bit 0
    ist die IRQ-Leitung aktiv, bis das Programm quittiert (`$D019` mit 1 beschreiben).
  - **CIA 1 Timer A** läuft aus dem Zyklenzähler (Latch `$DC04/$DC05`, Start/Neuladen über `$DC0E`, einmalig oder
    fortlaufend); ein Unterlauf setzt Bit 0 in `$DC0D` und mit gesetzter Maske die IRQ-Leitung. Lesen von `$DC0D` quittiert.
    Der KERNAL richtet so den 60-Hz-Takt ein (Latch `$4025`).
  - `$D019`/`$D01A`, die Farbregister und weitere VIC-Register lesen sich mit den unbenutzten Bits gesetzt;
    Sprite-Kollisionen (`$D01E/$D01F`) sind 0; `$D41B` (Oszillator 3) liefert Pseudo-Zufallszahlen, `$D419/$D41A` `$FF`,
    die übrigen SID-Register (nur schreibbar) 0.
  - **Tastatur/Joystick** (`$DC00/$DC01`): keine Taste gedrückt; Tasten gibt es über die KERNAL-Emulation (`keys`).
  - **Farb-RAM**: 4 Bit; die oberen vier Bits lesen sich als 0 (auf der Hardware unbestimmt).
  - I/O 1/2 (`$DE00–$DFFF`) liest sich als `$FF`.
- Nicht nachgebildet: CIA 1 Timer B, Uhrzeit (TOD), serielles Schieberegister, CIA 2 als NMI-Quelle, Lichtgriffel.
- **Interrupts von außen:** `interrupt` (Sitzung) bzw. `C64::setExternalIrq` hält die IRQ-Leitung zusätzlich aktiv,
  `nmi` löst einen NMI aus.

### Emulierte KERNAL-Aufrufe (`m6510::Kernal`)

Vorbild: die OS-Emulation (`m68k::AmigaOs`) des MC68000-Projekts. Ohne KERNAL-ROM erzeugt `Kernal::install()` ein eigenes
8-KiB-Abbild für `$E000–$FFFF`:

- Die **Sprungtabelle** ist echt: Einträge, die auf dem C64 über einen RAM-Vektor gehen, sind `JMP ($03xx)`
  (`CHROUT` → `JMP ($0326)` → `$F1CA`, ebenso `OPEN`, `CLOSE`, `CHKIN`, `CHKOUT`, `CLRCHN`, `CHRIN`, `STOP`, `GETIN`, `CLALL`,
  `LOAD` über `$F49E` und `($0330)`, `SAVE` über `($0332)`). Ein Programm, das einen Vektor umbiegt, wird also bedient wie
  auf dem echten Gerät.
- **IRQ-/NMI-Einsprung als echter 6502-Code** (`$FF48`: Register retten, `BRK` → `($0316)`, IRQ → `($0314)`; Standard-
  Handler `$EA31`: `UDTIM`, `$DC0D` quittieren, `$EA81` Register zurück, `RTI`; NMI `$FE43` → `($0318)`). Hardware-Vektoren
  `$FFFA` → `$FE43`, `$FFFC` → `$FCE2`, `$FFFE` → `$FF48`.
- Ein **Ausführungs-Hook** fängt jede andere Adresse des Bereichs ab, solange der KERNAL eingeblendet ist (`$01` mit
  HIRAM): bekannte Routinen werden nachgebildet, kehren mit `RTS` zurück und kommen ins Aufrufprotokoll; Aufrufe aus dem
  eigenen IRQ-Handler (`UDTIM` 60-mal je Sekunde) werden nicht protokolliert. Mit ausgeblendetem KERNAL läuft Code im RAM
  darunter ganz normal.

| Gruppe | Verhalten |
|---|---|
| `CHROUT` | Zeichen in die **Konsole** (PETSCII → Text, Steuerzeichen als `{CLR}`, `{RED}` …) **und** in den Bildschirmspeicher (Seite aus `$0288`, Cursor in `$D3/$D6`, Farbe aus `$0286`, `RETURN`, `CLR`, `HOME`, Cursortasten, `DEL`, Revers, Farbcodes, Zeichensatzumschaltung, Scrollen) |
| `GETIN`, `CHRIN` | nächste Taste aus dem Puffer (`keys`); leer: `GETIN` liefert 0, `CHRIN` RETURN |
| `STOP`, `SCNKEY` | STOP nicht gedrückt (`Z` = 0) / nichts |
| `PLOT`, `SCREEN`, `IOBASE`, `MEMTOP`, `MEMBOT`, `RDTIM`, `SETTIM`, `UDTIM`, `READST`, `SETMSG`, `SETTMO`, `SETLFS`, `SETNAM`, `VECTOR` | nachgebildet über die üblichen Zero-Page-/RAM-Adressen (Uhr in `$A0–$A2`, Status `$90`, Dateiparameter `$B7–$BC` …) |
| `LOAD` | Datei aus der angehängten Quelle (`attach`, nur mit `--allow-files`; Name aus `SETNAM`, Gerät ≥ 8), Sekundäradresse 0 = an `X/Y`, sonst an die Ladeadresse; `A` ≠ 0 = Verify; Ende in `X/Y` und `$AE/$AF`. Nicht gefunden: `C` = 1, `A` = 4 |
| `SAVE` | Bereich (`A` = Zero-Page-Zeiger auf den Anfang, `X/Y` = Ende) in die Liste gespeicherter Dateien |
| `OPEN`, `CLOSE`, `CHKIN`, `CHKOUT`, `CLRCHN`, `CLALL` | Tastatur/Bildschirm (Gerät 0/3): ohne Wirkung; für andere Geräte nur protokolliert (`emulated:false`) – Dateien gibt es nur über `LOAD`/`SAVE` |
| `CINT`, `IOINIT`, `RAMTAS`, `RESTOR` | wie nach dem Einschalten (VIC-Grundwerte, Bildschirm löschen, Port `$2F/$37`, CIA-Timer, Zero Page, Vektoren) |
| serieller Bus (`LISTEN`, `TALK`, `SECOND`, `TKSA`, `ACPTR`, `CIOUT`, `UNTLK`, `UNLSN`) | Status `$80` „Gerät nicht vorhanden“, protokolliert |
| andere Adressen im KERNAL (`JSR $E544` …) | protokolliert als unbekannter Einsprung, Rückkehr mit `C` = 0 |
| `$FFF6` | Rücksprungfalle von `run_program`: „program returned to BASIC“ |
| `BRK` (über `$0316` → `$FE66`) | hält an: „BRK at $xxxx“ |
| RESET (`$FCE2`) | Einschaltzustand herstellen, anhalten (ohne BASIC gibt es kein `READY.`) |

**Alles, was nicht nachgebildet ist, wird protokolliert** (`kernalcalls`: Adresse, Name, Aufrufstelle, Register vorher/
nachher, Hinweis) und kehrt mit `C` = 0 zurück – kein Blockieren, keine Abstürze.

**BASIC** wird nicht emuliert. Ein Programm mit BASIC-Starter (`10 SYS2061`) wird erkannt und mit `run_program` direkt an
der `SYS`-Adresse gestartet (wie `RUN`); andere BASIC-Programme werden detokenisiert angezeigt, aber nicht ausgeführt.

### Echte ROMs

BASIC (`$A000`, 8 KiB), KERNAL (`$E000`, 8 KiB) und Zeichensatz (4 KiB) können als eigene Kopie geladen werden
(`load_rom`, später Monitor `rom`). Sie sind urheberrechtlich geschützt und kommen **nie** ins Repository (`.gitignore`).
Ein geladenes KERNAL-ROM ersetzt die Emulation. Ohne BASIC- bzw. Zeichensatz-ROM liest sich der jeweilige Bereich auch bei
passendem `$01` als RAM. Der Kaltstart mit echten ROMs bis `READY.` ist ein lokaler Test (die CI läuft ohne ROMs, siehe
[Entscheidungen](roadmap.md#offene-fragen)); er braucht allerdings mehr Gerätemodell (Tastaturabfrage über CIA 1), als es
derzeit gibt.

Für Screenshots ohne Zeichensatz-ROM wird ein **eigener** Ersatzzeichensatz mitgeliefert (selbst gezeichnet, nicht aus dem
Original abgeleitet), damit Texte lesbar sind.

## Video: der Bildschirm als Bild

Wie beim CPC im Z80-Projekt soll ein Modell mit Bildverständnis den Bildschirm sehen. Gerendert wird **aus dem
Speicherzustand** (Registerstand am Ende, VIC-Sicht des Speichers), nicht zeilengenau:

| Modus | Register | Stand |
|---|---|---|
| Standard-Text (40×25, 16 Farben) | `$D011` Bit 5 = 0, `$D016` Bit 4 = 0 | Meilenstein 0.5 |
| Multicolor-Text | `$D016` Bit 4 = 1 | 0.5 |
| Extended Background Color | `$D011` Bit 6 = 1 | 0.5 |
| Hires-Bitmap (320×200) | `$D011` Bit 5 = 1 | 0.5 |
| Multicolor-Bitmap (160×200) | Bit 5 + Multicolor | 0.5 |
| Sprites (8, Hires/Multicolor, Vergrößerung) | `$D000–$D02E` | Idee |
| Rahmen, `$D020/$D021`, Scroll-Register, 38/24-Spalten-Modus | | 0.5 |
| Raster-Splits (Registerstand pro Zeile aus dem Schreibprotokoll) | | Idee |

Ausgabe: PNG (eigener Encoder ohne externe Bibliothek, wie im Z80-Projekt), Ausschnitt und Vergrößerung wählbar, dazu der
**Textinhalt** des Bildschirms als Zeichenkette (Bildschirmcodes → Text), damit auch ein Modell ohne Bildverständnis lesen
kann. Palette: siehe [offene Fragen](roadmap.md#offene-fragen).

## Dateiformate

PRG, P00, T64, D64, CRT – siehe [formats.md](formats.md). Ein Programm wird standardmäßig an seiner Ladeadresse abgelegt;
liegt sie bei `$0801` und beginnt mit einem BASIC-Starter, ist der Einsprung die `SYS`-Adresse.

## Umsetzung: `m6510::C64`, `m6510::Kernal`

- `C64(ram, cpu)` hängt sich an die `Cpu` (Lese-/Schreib-Overrides, Port-Hook, Trace-Hook für Raster und Timer).
  Speicher: 64 KiB RAM (`Memory`), ROM-Abbilder, Farb-RAM, Registerbänke der Bausteine.
- `peek()` (ohne Seiteneffekte), `write()` (wie der Prozessor: Port, I/O mit Protokoll, RAM unter ROM), `describeConfig()`,
  `screenAddress()`/`vicBank()`, `takeIoLog()`, `state()`/`setState()` für Checkpoints und Snapshots.
- `Kernal(c64, cpu, ram)`: `install()`, `coldStart()`, `startProgram(entry)`, `takeConsole()`, `takeCalls()`, `addKeys()`,
  `files` (Quelle für `LOAD`), `saved` (Ergebnis von `SAVE`), `state()`/`setState()` (Tastenpuffer).
- Sitzung: `machine c64` ([agent-protocol.md](agent-protocol.md)); `generic` bleibt 64 KiB RAM ohne Prozessorport.
- Tests: Suite `c64` (alle acht `$01`-Konfigurationen, Schreiben unter ROM, Protokoll mit Spiegeln und Namen, Raster-
  Warteschleife, Raster-IRQ, Timer-IRQ, KERNAL-Programm mit `CHROUT`/`GETIN`/`PLOT`/`SCREEN`, umgebogener `CHROUT`-Vektor,
  Jiffy-Uhr über den IRQ, `LOAD`, `BRK`, unbekannte Einsprünge, ausgeblendeter KERNAL, Zustände).
